# SW 정리 — 무엇을 왜 바꿨나

코드 변경만 보면 이해하기 어려워서, 바꾼 내용과 이유를 여기에 모았다.
PR은 커밋 5개로 나뉘어 있고, 커밋 순서대로 읽으면 따라가기 쉽다.

1. 이전 실험 스크립트를 `archive/`로 이동
2. 빠져 있던 `models.py` 추가 (원본 그대로)
3. 낙상 탐지와 PPG 코드를 폴더로 분리 (내용 변경 없음)
4. 실시간(창 단위) 평가와 판정 1회 지연 측정 추가 — **가장 큰 변경**
5. 문서·설정 (이 파일, README, requirements, .gitignore)

## 요약

- **옛 스크립트 7개는 `archive/`로 옮겼다.** 라벨·센서·분할 문제로 결과를 믿을 수 없다. 이유는 `archive/README.md`
- **`compare_models.py`는 실행이 안 됐다.** 불러오는 `models.py`가 저장소에 없었다. 원본을 그대로 추가했다
- **평가를 실시간 방식으로 바꿨다.** 기록 전체를 한 번에 넣던 평가를, 최근 몇 초(창)를 밀어가며 판정하는 방식으로 바꿨다. 추론 속도도 판정 1회를 기준으로 잰다
- **창 길이와 판정 간격은 실험으로 정했다.** 후보와 고르는 규칙을 먼저 정하고, 테스트는 쓰지 않았다
- **안경 펌웨어의 판정 규칙을 기준선으로 넣었다.** 실제 제품에 들어가는 알고리즘이라, 모델이 이보다 나아야 의미가 있다
- **단위를 안경에 맞췄다.** 가속도 g, 자이로 °/s

`models.py`의 여섯 모델은 한 줄도 바꾸지 않았다. 모델은 그대로 두고 "무엇을 넣고 어떻게 평가하는가"만 바꿨다.

## 2. 핵심 변경: 실시간 평가

### 이전 방식의 문제

`compare_models.py`는 기록 하나(머리 센서, 중앙값 약 17초)를 `detector.score(record.raw)`에 통째로 넣어 점수 하나를 받고, 그 호출 시간을 "추론 속도"로 기록했다.

1. **시간이 판정 1회의 시간이 아니다.** 안경은 샘플을 계속 받으면서(데이터는 25Hz, 안경은 100Hz) 최근 몇 초만 보고 주기적으로 판정한다. 기록 전체를 처리한 시간은 기록 길이에 따라 늘어나고, 실제 판정 1회의 시간과 다르다
2. **성능도 부풀려진다.** 피처(평균·분위수·최솟값 등)를 기록 전체에서 계산하니, 넘어진 뒤 바닥에 누워 있는 구간까지 다 보고 판정하는 셈이다. 실시간으로 판정하는 순간에는 그 뒤의 데이터가 아직 없다

### 바뀐 방식

```
기록 ──────────────────────────────────────────────────────▶ 시간
   [──── 창 W초 ────]                               판정
        [──── 창 W초 ────]                          판정 (판정 간격만큼 뒤)
             [──── 창 W초 ────]                     판정
                                  ▲ 충격
                                  ├──── 인정 구간 5초 ────┤
```

- **창(window)**: 판정 한 번에 보는 최근 데이터 W초
- **판정 간격(hop)**: 판정을 몇 초마다 하는가
- **충격 시점**: 낙상 기록에서 가속도 크기가 가장 큰 샘플. 데이터에 충격 시각 표시가 없어서 이렇게 정했다
- **인정 구간**: 충격 뒤 5초 안에 알람이 울리면 그 낙상을 잡은 것으로 본다

기록 단위로 결과를 모은다.

- **낙상 기록**: 인정 구간 안에 끝나는 창 중 하나라도 임계값을 넘으면 탐지 → **재현율**
- **일상동작 기록**: 어느 창이든 하나라도 넘으면 오경보 → **특이도**(= 1 − 오경보 비율)
- **탐지 지연**: 충격부터 첫 알람까지 걸린 시간
- **판정 1회 지연**: 창 하나를 넣어 점수가 나올 때까지(피처 계산 포함). 창을 한 번에 하나씩 넣고, 평균 대신 중앙값과 상위 99% 값을 쓴다. 가끔 느린 판정이 실시간에서는 문제가 되기 때문이다

학습도 창 단위로 한다 (`streaming.training_windows`).

- 일상동작 기록: 모든 창 = 정상(0)
- 낙상 기록: 충격 샘플을 포함하는 창 = 낙상(1), 충격 1초 전보다 먼저 끝나는 창(서 있거나 걷는 중) = 정상(0)
- 그 사이의 창(넘어지기 시작하는 순간)과, 충격이 창에서 빠져나간 뒤의 창(누워 있는 중)은 애매해서 학습에 쓰지 않는다

### 정해 둔 값과 이유

| 값 | 이유 | 바꿔야 할 때 |
|---|---|---|
| 인정 구간 5초 | 펌웨어 규칙은 충격 뒤 최대 3초에 0.75초 정지 확인을 더해 판정한다. 그보다 넉넉하게 잡았다 | "몇 초 안에 알려야 하는가"가 정해지면 그 값으로 |
| 충격 1초 전 제외 | 넘어지는 동작이 시작되는 구간이라 정상으로 보기 어렵다 | |
| 목표 재현율 80% | 멘토 지침 그대로 | |

## 3. 창 길이·판정 간격 — 실험으로 정했다

`select_window.py`. 개발(dev) 참가자 안에서만 참가자 단위 4묶음 교차검증을 했고, 테스트 참가자는 쓰지 않았다.

**후보와 이유**

- **창 2·3·4·6초**: 낙상 판정에는 충격과 그 직후(움직임 없음, 자세 변화)가 함께 보여야 한다. 펌웨어는 충격 뒤 최대 3초를 본다. 2초는 충격과 직후가 겨우 들어가는 짧은 쪽, 6초는 기록 길이(약 17초)에 비해 여유 있는 긴 쪽이다. 창이 길면 정보는 늘지만 알람이 늦어질 수 있고 계산이 는다
- **판정 간격 0.2·0.4·1.0초**: 간격이 길면 계산(배터리)이 줄지만 알람이 최대 그만큼 늦어진다. 25Hz에서 샘플 수가 정수(5·10·25개)인 값으로 골랐다

**고르는 규칙 (결과를 보기 전에 정했다)**

1. 모델마다 따로 고른다. 창 길이는 모델의 설정값이라 모델마다 맞는 값이 다를 수 있다
2. 기준: 재현율 80% 지점의 특이도(기록 단위), 묶음 평균
3. 최고 평균에서 그 설정의 묶음 간 표준편차 안에 드는 설정은 동률로 본다
4. 동률이면 창이 짧은 쪽(알람이 빠르고 계산이 적다), 그다음 판정 간격이 긴 쪽(계산이 적다)

**결과**

| 모델 | 고른 창 | 고른 간격 | 특이도 (재현율 80%, 4묶음 평균 ± 표준편차) | 탐지 지연 중앙값 |
|---|---|---|---|---|
| LightGBM | 4초 | 1.0초 | 0.976 ± 0.013 | 0.74초 |
| 로지스틱 회귀 | 2초 | 1.0초 | 0.930 ± 0.019 | 0.52초 |
| IQR | 2초 | 1.0초 | 0.698 ± 0.032 | 0.48초 |
| Robust Z | 2초 | 1.0초 | 0.667 ± 0.035 | 0.48초 |
| 오토인코더 | 2초 | 1.0초 | 0.630 ± 0.038 | 0.64초 |
| Moving Z | 3초 | 1.0초 | 0.569 ± 0.105 | 0.47초 |

- **판정 간격은 모두 1.0초가 골라졌다.** 간격을 줄여도 특이도가 오르지 않았다. 판정을 자주 할수록 일상동작 중에 오경보가 날 기회도 늘어나기 때문이다. 1초 간격에서도 탐지 지연은 중앙값 0.5~0.7초다
- **동률 규칙이 결과를 바꾼 경우가 둘 있다.** 로지스틱 회귀는 4초(0.944 ± 0.019)가 최고였지만 2초(0.930)가 표준편차 안이라 2초를 골랐다. Moving Z는 6초·0.2초(0.635 ± 0.093)가 최고였지만 묶음 간 편차가 커서 3초·1.0초가 동률에 들어갔다
- 전체 표는 실행하면 `results/window_selection/selection_table.csv`에 생긴다

## 4. 펌웨어 규칙을 기준선으로

`firmware_rule.py`는 HW 펌웨어(PR #5)의 `src/core/fall.c`를 파이썬으로 옮긴 것이다. 판정 순서는 이렇다.

1. **충격**: 가속도 크기 ≥ 3g, 또는 ≥ 2g 이면서 최근 2초 대비 z ≥ 6
2. 충격 뒤 3초 안에 **조용함**(가속도 0.7~1.3g, 자이로 약 30°/s 미만) + **기울어짐**(충격 전 중력 방향과 45° 넘게 다름)이 0.75초 이어지면 **낙상 의심**

- **왜 기준선인가**: 실제 안경에 들어가는 판정이다. 모델이 이것보다 낫지 않다면 모델을 쓸 이유가 없다
- **어떻게 옮겼나**: 상수를 하나도 바꾸지 않으려고 25Hz 데이터를 100Hz로 보간하고 센서 원시값 단위(±16g, ±2000°/s)로 바꿔서 넣는다
- **검증**: 펌웨어의 `fall.c`를 그대로 컴파일해 같은 입력을 넣고 비교했다. 기록 300개에서 충격·낙상 의심 이벤트의 시각이 모두 같았다

**결과**

- 교차검증(dev): 재현율 0.42, 특이도 0.99 ± 0.01
- 테스트: 재현율 0.38, 특이도 0.98, 탐지 지연 중앙값 1.6초 (충격 뒤 0.75초 정지를 확인하고 판정하기 때문)

오경보는 거의 없지만 낙상의 절반 이상을 놓친다. 전체 낙상 1,767개를 판정 단계별로 나누면 이렇다.

- **22%는 충격 조건(3g)이 걸리지 않는다.** 이 데이터에서 머리 가속도 최고값의 중앙값이 2.97g다. 25Hz 데이터는 짧은 충격의 최고값을 놓치므로, 실제 기기(100Hz)에서는 이보다 더 걸릴 수 있다
- **36%는 충격은 잡지만 3초 안에 "조용함 + 기울어짐" 확인을 통과하지 못한다.** "넘어졌다 일어남" 4종(905·906·914·916)은 탐지율이 14%다. 넘어진 뒤 바로 움직이니 설계상 잡히지 않는다. 옆으로 엎어져 눕는 낙상(907·908)도 19~22%로 낮은데, 원인은 HW 쪽과 함께 확인할 과제다
- **42%가 낙상 의심까지 간다**

## 5. 단위와 샘플링을 안경에 맞췄다

- **단위**: 데이터는 가속도 m/s², 자이로 rad/s다. 펌웨어(BMI270 ±16g, ±2000°/s)에 맞춰 g와 °/s로 바꿨다 (`data.read_recording`). 여섯 모델은 모두 표준화·중앙값·트리 분할을 쓰므로 단위 배율이 바뀌어도 결과는 같다. 나중에 안경 데이터를 그대로 넣을 수 있게 하려는 것이다
- **샘플링**: 데이터는 25Hz, 안경은 100Hz다. HW PR #5의 펌웨어에는 원시 데이터를 솎아 보내는 설정(`Kconfig`의 100Hz ÷ N, N=1~10)이 있어서 N=4로 하면 25Hz로 받을 수 있다. 그러면 지금 모델을 그대로 쓸 수 있다

## 6. 결과

`run_streaming.py`. 테스트 참가자 4명(101·102·106·208, 낙상 408개 / 일상동작 348개)이고, `compare_models.py`와 같은 참가자다. 임계값은 검증 참가자 4명에서 재현율 80%가 되도록 정해 테스트에 그대로 적용했다. 그래서 테스트 재현율은 80%와 조금씩 다르다.

|---|---|---|---|---|---|---|
| **LightGBM** | 4초·1초 | 0.767 | **0.977** | 8건 | 0.68초 | 87 / 94µs |
| 로지스틱 회귀 | 2초·1초 | 0.748 | 0.911 | 31건 | 0.52초 | 163 / 175µs |
| IQR | 2초·1초 | 0.821 | 0.635 | 127건 | 0.48초 | 9.7 / 10.1µs |
| Robust Z | 2초·1초 | 0.792 | 0.592 | 142건 | 0.48초 | 8.9 / 9.2µs |
| Moving Z | 3초·1초 | 0.760 | 0.592 | 142건 | 0.48초 | 19.9 / 22.7µs |
| 오토인코더 | 2초·1초 | 0.809 | 0.580 | 146건 | 0.64초 | 165 / 177µs |

판정 1회 지연은 노트북 CPU 1스레드에서 파이썬으로 잰 값이다. 라즈베리파이에서는 더 느리겠지만 모델 간 순서는 비슷할 것이다. 1초에 한 번 판정하므로 가장 느린 오토인코더도 1초의 0.02%만 쓴다. 펌웨어 규칙은 파이썬으로 옮긴 코드라 실제 기기(C)와 시간이 다르다.

**볼 것**

1. **LightGBM이 가장 좋다.** 오경보는 펌웨어 규칙과 같은 수준(348건 중 8건과 7건)인데, 재현율은 두 배(0.77과 0.38)다
2. **실시간 평가로 바꾸자 일부 모델이 크게 떨어졌다.** 같은 테스트 참가자로 비교한 결과다

   | 방법 | 이전 방식 (기록 전체) 재현율 / 특이도 | 실시간 재현율 / 특이도 |
   |---|---|---|
   | LightGBM | 0.765 / 0.986 | 0.767 / 0.977 |
   | 로지스틱 회귀 | 0.757 / 0.980 | 0.748 / 0.911 |
   | 오토인코더 | 0.723 / 0.842 | 0.809 / 0.580 |
   | IQR | 0.821 / 0.632 | 0.821 / 0.635 |
   | Robust Z | 0.770 / 0.618 | 0.792 / 0.592 |
   | Moving Z | 0.779 / 0.618 | 0.760 / 0.592 |

   - 로지스틱 회귀는 오경보가 7건에서 31건으로 늘었다. 기록 전체를 볼 때는 넘어진 뒤 누워 있는 구간까지 피처에 들어가 쉽게 구분됐던 것으로 보인다. 실시간으로 판정하는 순간에는 그 정보가 없다
   - LightGBM은 거의 그대로다. 실시간에서도 믿을 만하다
   - 오토인코더는 재현율이 달라 직접 비교하기 어렵지만 특이도가 크게 떨어졌다
3. **통계 방법 3종은 두 방식 모두 특이도 0.6 안팎이다.** 오경보가 걷는 동작에 몰려 있다. Robust Z는 걷기·조깅·절뚝 걷기·비틀거림·걸려 휘청 기록에서 100% 오경보가 났고, 쪼그려 앉기·허리 굽히기에서는 0%였다. "학습한 일상동작과 다르다"는 기준만으로는 머리가 크게 흔들리는 걷기와 낙상을 가르기 어렵다

**한계**

- 테스트 참가자가 4명뿐이라 숫자가 흔들릴 수 있다. 오경보 8건과 7건처럼 작은 차이는 같다고 봐야 한다
- 25Hz 데이터이고, 젊은 지원자가 매트 위에서 연기한 낙상이다
- 충격 시점을 가속도 최댓값으로 추정했다
